# Apple iPhone Stock Watcher: Design

- **Date:** 2026-09-21
- **Status:** Approved design, pending implementation plan
- **Target:** iPhone 18 Pro Max 512GB Burgundy, Apple Store pickup, UAE

## 1. Problem

Apple UAE lists the iPhone 18 Pro Max 512GB Burgundy at 6,349 AED with a 3 to 4 week
dispatch estimate and no in-store pickup availability at any of the five UAE stores.
Pickup inventory does appear, but it is claimed within hours. Manually refreshing the
product page is the only way to catch it, which does not scale to a multi-week wait.

This project polls Apple's availability endpoint on a schedule and pushes a phone
notification the moment the watched configuration becomes collectable.

## 2. Goals and non-goals

**Goals**

1. Detect pickup availability for a configurable set of iPhone SKUs at a configurable
   set of UAE Apple Stores.
2. Push a high-priority notification to the owner's iPhone within one polling interval
   of stock appearing.
3. Run without depending on any personal machine being powered on.
4. Let the owner widen or narrow what is watched by editing one config file, with no
   code changes.

**Non-goals**

1. No web UI or dashboard. The phone notification is the entire interface.
2. No automated purchasing. The notification links to Apple's buy page and the human
   takes it from there.
3. No delivery-date tracking in v1. The endpoint for it is identified below and the
   work is additive, but it is not what was asked for.
4. No support for Apple storefronts outside the UAE in v1.

## 3. Findings from the spike (verified live on 2026-09-21)

Everything in this section was confirmed against apple.com, not assumed.

### 3.1 Working endpoints

| Endpoint | Status | Purpose |
|---|---|---|
| `GET /ae/shop/retail/pickup-message` | 200, JSON | Per-store pickup availability. **This is the one we use.** |
| `GET /ae/shop/delivery-message` | 200, JSON | Dispatch estimate ("3 to 4 weeks"). Reserved for a later phase. |
| `GET /ae/shop/fulfillment-messages` | 541, HTML | Dead on the UAE storefront. Do not use. |
| `GET /ae/shop/pickupEligibility` | 404 | Does not exist. |

Canonical request:

```
https://www.apple.com/ae/shop/retail/pickup-message
  ?pl=true&mts.0=regular&parts.0=<PART_NUMBER>&location=Abu+Dhabi
```

A single request with `location=Abu+Dhabi` returns **all five UAE stores** sorted by
distance. Store filtering is therefore a local concern, and widening coverage to the
whole country costs no additional requests.

### 3.2 Store table

Apple's payload carries `storeNumber`, `storeName`, `city` and `storedistance`. The
`state` field exists but is **empty for every UAE store**, so emirate is not available
from the API and must be supplied by us.

| storeNumber | storeName | city (from API) | Emirate (ours) | Distance from Abu Dhabi |
|---|---|---|---|---|
| R706 | Al Maryah Island | Abu Dhabi | Abu Dhabi | 9.44 km |
| R595 | Yas Mall | Abu Dhabi | Abu Dhabi | 19.47 km |
| R596 | Mall of the Emirates | Dubai | Dubai | 109.47 km |
| R597 | Dubai Mall | Dubai | Dubai | 121.02 km |
| R785 | Al Jimi Mall | Al Ain | Abu Dhabi | 132.89 km |

Al Jimi Mall is the trap: it sits in the **emirate** of Abu Dhabi but the **city** of
Al Ain, and it is farther away than either Dubai store. A naive `city == "Abu Dhabi"`
filter silently excludes it. The config must let the user express either intent
explicitly.

`storeNumber` is used as the internal key because it survives store renames.

### 3.3 SKU catalog

Part numbers were extracted from the product page's embedded JSON, which exposes
`partNumber` alongside `dimensionCapacity`, `dimensionScreensize` and `dimensionColor`.
The full UAE iPhone 18 Pro lineup is 31 SKUs. The target is **`MJXC4AH/A`**
(512gb / 6_9inch / burgundy).

Dimension vocabularies:

- `dimensionColor`: `burgundy`, `black`, `silver`, `glacier`
- `dimensionCapacity`: `256gb`, `512gb`, `1tb`, `2tb`
- `dimensionScreensize`: `6_3inch` (Pro), `6_9inch` (Pro Max)

Part numbers are not stable across Apple lineup revisions, so they are treated as
derived data (`catalog.json`), regenerated by a script rather than hand-edited.

### 3.4 Observed `pickupDisplay` states, and why the match rule is a denylist

Two states were observed live:

| Value | Meaning | Seen at |
|---|---|---|
| `unavailable` | No stock for same-day pickup | All stores, burgundy 512 |
| `ineligible` | Not offered for pickup at that store | Dubai Mall, black 512 |

The positive value was **never observed**. At 07:55 on 2026-09-21 the owner's
screenshots showed black, glacier and silver 512GB as "Available Wed 23 Sep" at Dubai
Mall; by the evening of the same day that SKU had flipped to `ineligible`. The stock
was claimed inside one day, which both confirms the premise of the project and denied
us a positive fixture.

Two consequences, and they are the most important decisions in this document:

1. **The match rule is a denylist.** A store counts as a hit when
   `pickupDisplay not in {"unavailable", "ineligible"}`. Matching on an assumed literal
   `"available"` risks a watcher that never fires and looks identical to "no stock",
   which is the worst possible failure for this project.
2. **Any unrecognised `pickupDisplay` value is reported, not swallowed.** It is treated
   as a hit and the raw value is included in the notification.

The human-readable quote lives in `pickupSearchQuote` (for example
`"Currently unavailable"`, and per the screenshots `"Available Wed 23 Sep"` when stock
exists). This string is passed through verbatim into the notification so the owner sees
the actual pickup date rather than our interpretation of it.

Note also that this endpoint is same-day scoped: `notAvailableNearby` reads "Not
available **today** at [X] nearest stores." Future-dated pickup offers surface through
`pickupSearchQuote`, which the denylist rule captures correctly.

## 4. Architecture

One scheduled job, one outbound request per run, no browser automation.

```
GitHub Actions cron (*/5)
        |
        v
  applewatch.cli
        |
   1. load watches.yml + stores.yml + catalog.json
   2. resolve watch rules -> set of part numbers
   3. GET /ae/shop/retail/pickup-message (single call, all parts, all stores)
   4. parse -> [(storeNumber, storeName, city, sku, pickupDisplay, quote)]
   5. apply rules -> hits
   6. diff against state.json -> events
   7. POST events to ntfy.sh
   8. write state.json, commit when changed
```

Module boundaries, each independently testable:

| Module | Responsibility | Depends on |
|---|---|---|
| `catalog.py` | Resolve (model, screen, capacity, color) to part numbers | `catalog.json` |
| `apple.py` | Build the request, call Apple, parse to flat records | network |
| `rules.py` | Apply watch rules to records, decide what is a hit | pure |
| `state.py` | Load/save state, diff current against previous, emit events | filesystem |
| `notify.py` | Render and POST ntfy messages | network |
| `cli.py` | Wire the above, handle flags | all |

`rules.py` and `state.py` are pure functions over plain data, which is where the logic
that can actually be wrong lives. They get the test coverage.

## 5. Configuration

### 5.1 `watches.yml`

```yaml
ntfy_topic_env: NTFY_TOPIC
poll_location: Abu Dhabi
reminder_minutes: 30

watches:
  - name: "Burgundy 512 Pro Max, Abu Dhabi city"
    model: iphone18pro
    screen: 6_9inch
    capacity: [512gb]
    color: [burgundy]
    cities: [Abu Dhabi]
    priority: urgent

  # Uncomment to include Al Jimi Mall (Al Ain, Abu Dhabi emirate, 133 km):
  # - name: "Burgundy 512 Pro Max, whole Abu Dhabi emirate"
  #   screen: 6_9inch
  #   capacity: [512gb]
  #   color: [burgundy]
  #   emirates: [Abu Dhabi]
  #   priority: urgent
```

### 5.2 Field reference

| Field | Type | Omitted means | Matches against |
|---|---|---|---|
| `name` | string | required | label used in notifications |
| `model` | string | any model | `familyType` |
| `screen` | string | any size | `dimensionScreensize` |
| `capacity` | list | any capacity | `dimensionCapacity` |
| `color` | list | any color | `dimensionColor` |
| `stores` | list | no store constraint | `storeNumber` or exact `storeName` |
| `cities` | list | no city constraint | API `city` field, literal |
| `emirates` | list | no emirate constraint | our `stores.yml` mapping |
| `max_distance_km` | number | no distance constraint | `storedistance` |
| `priority` | enum | `urgent` | ntfy tier of this watch's in-stock alert |

`priority` accepts `urgent` (ntfy 5), `high` (4), `default` (3) or `low` (2). It sets the
tier of the **in-stock** alert only. Reminder and gone-again alerts are fixed at 3 and 2
regardless of the watch's priority, so a noisy watch cannot spam the owner with urgent
reminders.

### 5.3 Matching semantics

These rules are stated explicitly because the Al Jimi case proved they are not obvious:

1. **Product fields AND together.** `capacity: [512gb]` plus `color: [burgundy]` matches
   only 512GB burgundy.
2. **Values within one field OR together.** `color: [burgundy, black]` matches either.
3. **Store selectors OR across each other.** `stores`, `cities` and `emirates` all answer
   the same question ("which stores?"), so a store matches if it satisfies *any* of them.
   Specifying `cities: [Abu Dhabi]` and `emirates: [Abu Dhabi]` in one rule yields all
   three emirate stores, not the intersection.
4. **`max_distance_km` is a constraint, not a selector, so it ANDs.** It trims whatever
   the selectors produced. `emirates: [Abu Dhabi]` with `max_distance_km: 25` gives
   R706 and R595 but excludes Al Jimi Mall at 133 km. Used alone, it selects purely by
   distance.
5. **An omitted field is not a constraint**, it is a wildcard.
6. A watch with no location filter at all watches every UAE store.

### 5.4 `stores.yml` and `catalog.json`

`stores.yml` is the hand-maintained source of truth for the store table in section 3.2,
carrying the emirate mapping Apple does not provide. `catalog.json` is generated data
(31 SKUs), regenerated by `scripts/refresh_catalog.py`, which re-scrapes the product
page's embedded JSON.

## 6. State and alert policy

`state.json` is committed back to the repository, keyed by `sku|storeNumber`:

```json
{
  "MJXC4AH/A|R595": {
    "status": "unavailable",
    "quote": "Currently unavailable",
    "since": "2026-09-21T20:14:00+04:00",
    "last_notified": null
  }
}
```

Event table:

| Transition | Priority | Message |
|---|---|---|
| not-hit to hit | 5 (urgent) | `IN STOCK: Burgundy 512 Pro Max at Yas Mall` plus the raw quote, plus tap-to-open buy link |
| hit sustained, `reminder_minutes` elapsed | 3 (default) | `Still in stock at Yas Mall (47 min)` |
| hit to not-hit | 2 (low) | `Gone from Yas Mall after 52 min` |
| unknown `pickupDisplay` value | 4 | `Unexpected state "<value>" at Yas Mall`, treated as a hit |

Committing state serves three purposes beyond deduplication: it survives the ephemeral
Actions container, it produces a timestamped restock history useful for learning when
Apple UAE actually drops inventory, and it keeps the repository active. GitHub disables
scheduled workflows after 60 days of repository inactivity, so the job additionally
writes a once-daily heartbeat commit.

All timestamps render in `Asia/Dubai`.

## 7. Notifications

ntfy.sh, free tier, no account required. The topic name is the only secret, so it must
be unguessable (for example `apple-ae-burgundy-k7f2q9x`) and is stored in the GitHub
Actions secret `NTFY_TOPIC`, never committed.

Messages carry a `Click` header pointing at the buy page so the notification is one tap
from checkout, and `Tags` for a visual marker.

Owner-side setup is documented step by step in the README, including enabling iOS Time
Sensitive notifications and allowlisting ntfy in the sleep Focus. Without that last
step an overnight restock alert is suppressed by Do Not Disturb, which defeats the
project.

## 8. Repository layout

`apple-iPhone-stock-watcher`, **public**.

Public is a deliberate technical choice, not an oversight: GitHub Actions minutes are
unlimited on public repositories but capped at 2,000 per month on private ones. Polling
every five minutes bills roughly 8,600 minutes per month, which exhausts the private
allowance in about a week. Nothing in the repository is sensitive once the ntfy topic
lives in a secret.

```
watches.yml
stores.yml
catalog.json
state.json
src/applewatch/{__init__,catalog,apple,rules,state,notify,cli}.py
scripts/refresh_catalog.py
tests/fixtures/{pickup_unavailable,pickup_ineligible,pickup_available_synthetic}.json
tests/test_{rules,state,catalog,apple}.py
.github/workflows/check.yml
README.md
```

## 9. Workflow

`.github/workflows/check.yml`:

- `schedule: cron: "*/5 * * * *"` plus `workflow_dispatch` for manual runs.
- `permissions: contents: write` for the state commit.
- `concurrency: {group: check, cancel-in-progress: false}` so overlapping runs cannot
  race the commit.
- Commit messages carry `[skip ci]`.
- `NTFY_TOPIC` injected from repository secrets.

GitHub's scheduled runs drift under load, so a nominal 5 minute interval is realistically
5 to 15 minutes. This is accepted for v1 and revisited only if observed restock windows
prove shorter than the drift.

## 10. Error handling

The dangerous failure is the silent one, where the checker breaks and its silence is
indistinguishable from "no stock".

| Failure | Handling |
|---|---|
| Non-200 or unparseable JSON | Retry 3 times with exponential backoff, then a low-priority "checker is broken" alert, rate limited to once per 6 hours |
| `head.status` not `"200"` in body | Same as above |
| Watched SKU absent from `partsAvailability` | Part numbers rotated. Error, not "unavailable". Alert once and instruct running the catalog refresh |
| Unknown `pickupDisplay` value | Treated as a hit and surfaced, per section 3.4 |
| ntfy POST fails | Retry 3 times, then fail the workflow run loudly so it shows in the Actions tab |

A single request every five minutes with a browser User-Agent is comparable to a person
refreshing the product page, which is the polite end of the range.

## 11. Testing

- `rules.py` and `state.py` are pure and get direct unit tests: matching semantics from
  section 5.3 (especially the Al Jimi city-versus-emirate case), and every transition in
  the section 6 event table.
- `apple.py` parses against **real recorded payloads**: `pickup_unavailable.json`
  (burgundy, all five stores) and `pickup_ineligible.json` (black at Dubai Mall), both
  captured live on 2026-09-21.
- No positive payload could be captured, so `pickup_available_synthetic.json` is derived
  from the real structure with `pickupDisplay` and `pickupSearchQuote` altered. It is
  named `_synthetic` so no reader mistakes it for observed data. The denylist rule in
  section 3.4 exists precisely because this fixture is a guess.
- `--dry-run` prints resolved SKUs, matched stores and the notifications that would fire,
  without sending. This is the documented way to validate a config change before
  committing it.
- `--force-notify` smoke-tests the ntfy path end to end.

## 12. README requirements

The README is a deliverable, not an afterthought. It must contain:

1. What the project does and the one-line summary of how.
2. **Configuring watches**: the full field reference (5.2), every valid value enumerated,
   the store table (3.2), the matching semantics (5.3) with the Al Jimi worked example,
   and four recipes: strict default, single store any color, whole emirate, everything
   512GB nationwide.
3. ntfy setup, step by step, including the iOS Focus allowlist step.
4. GitHub setup: fork or clone, set `NTFY_TOPIC`, enable Actions.
5. How to validate a config change with `--dry-run` before committing.
6. Troubleshooting: empty matches, rotated part numbers, disabled cron after inactivity.
7. A plain statement that this reads a public availability endpoint at human refresh
   rates and does not automate purchasing.

## 13. Open decisions

1. **Al Jimi Mall in the shipped default.** Current default watches R706 and R595 only,
   with the emirate-wide variant commented in `watches.yml`. The owner's approval message
   was truncated before this was confirmed. Flipping it is a one-line change.

## 14. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Positive `pickupDisplay` value differs from any guess | High | Denylist matching (3.4). This is the whole reason for that design. |
| Apple rotates part numbers | Medium | `catalog.json` is derived, `refresh_catalog.py` regenerates, missing SKU raises an alert |
| Apple changes or removes the endpoint | Low | Loud failure alerts rather than silence |
| Actions cron drift exceeds restock window | Medium | Accepted for v1. Fallback is a local or Cloudflare Worker runner on the same code |
| Actions cron disabled after 60 days idle | Medium | Daily heartbeat commit |
| Overnight alert suppressed by iOS Focus | High if unhandled | README setup step, priority 5 with Time Sensitive |
